网页里出现了一篇完整的技术文章，并不意味着抓取之后就能得到完整的技术文本。导航栏可能占据一半字符，公式可能在抽取时消失，代码缩进可能被规范化破坏，而正文又可能因为包含大量英文术语，被中文过滤器判成“不够中文”。

清洗的任务是从原始表示中恢复适合当前训练目标的内容，同时保留足够的信息来解释每次修改。**清洗规则不仅决定数据是否干净，也决定哪些文体和知识还能进入模型。**

本文是“大模型训练研究笔记”第一卷第二篇。可以先读[语料地图与选型框架](/posts/2026-10-15-llm-training-data-01-map/)；下一篇将讨论[模型质量评分](/posts/2026-10-15-llm-training-data-03-quality/)。

## 一、从一张网页开始

下面是一段自写的教学示例，不是实际语料抽样。它刻意把几类常见内容放在一起。

```html
<nav>首页 / 推荐 / 登录 / 下载客户端</nav>
<article>
  <h1>为什么梯度累积不能减少参数内存</h1>
  <p>梯度累积改变每次更新使用的样本组织方式。</p>
  <p>Parameters、gradients 和 optimizer states 仍然需要存储。</p>
  <pre>if ready:
    optimizer.step()</pre>
</article>
<aside>相关阅读：点击领取优惠券</aside>
<footer>联系我们：editor@example.org</footer>
```

如果只去除 HTML 标签，导航、广告和联系信息仍会留在正文中。如果把所有连续空白压成一个空格，代码结构会损坏。如果删除所有含英文的行，文章最关键的解释会缺失。如果把邮箱所在的整页丢弃，又会连带删除正常正文。

这几种错误对应不同层次：抽取器识别正文，规范化处理表示，过滤器判断去留，脱敏器处理特定片段。把它们全塞进一个没有中间输出的 `clean(text)`，会让错误难以定位。

## 二、选择输入格式决定了能修复什么

Common Crawl 的 **WARC** 保存抓取内容与相关记录，**WET** 提供提取出的文本，**WAT** 提供派生元数据。选择 WET 可以省去自己处理 HTML 的步骤，但也接受了上游抽取已经做出的决定；从 WARC 开始则有机会更换正文抽取器，代价是额外的处理成本。[官方格式说明](https://commoncrawl.org/get-started)

这个区别可以用一个无法逆转的例子说明：如果上游抽取器已经把表格中的行列关系丢掉，下游过滤器无法仅凭一串数字恢复原表。保存来源位置和原始对象的校验和，因此不仅服务于“以后查出处”，还决定了能否重新运行更好的抽取过程。

已清洗的 Parquet 或 JSONL 也可以是合理起点。只是研究问题应相应缩小：对这些文件执行质量筛选，是在研究“现有正文怎样选择”，不能声称已经比较了“原始网页怎样抽取”。

## 三、正文抽取需要保留语义结构

正文抽取通常利用 DOM 结构、文本密度、链接比例与页面布局线索，识别主体内容。文章页、论坛、API 文档和商品页的结构不同，同一个抽取器可能表现不同。

FineWeb 的抽取实验对比了 WET 与从 WARC 使用 trafilatura 提取的文本，在其训练设置中后者得到更好的下游表现。这个案例支持“抽取步骤值得单独评估”，而不是所有网页都必须使用同一工具。[FineWeb 论文 §3.2](https://arxiv.org/html/2406.17557v1#S3.SS2)

选抽取器时，可以先建立一组固定页面：新闻、博客、中文论坛、中英混排教程、带代码文档、包含表格的说明页。检查的不只是输出字数，而是正文边界和信息关系。

| 页面部分 | 希望保留的关系 | 常见破坏 |
| --- | --- | --- |
| 标题与小节 | 标题属于后续哪段正文 | 标题被丢弃或合并到导航 |
| 列表 | 项目边界与层级 | 多条条件拼成一段 |
| 代码 | 换行、缩进、语言标记 | 全部压成普通句子 |
| 表格 | 行、列、表头关系 | 只剩无上下文数字 |
| 论坛 | 提问、回答、引用边界 | 多个发言者混成一人 |

人工评估时，应同时查看原页面的内容表示和抽取结果。只给审查者看输出，容易把“读起来很流畅但缺了关键段落”的文本误判为好结果。

正文保留也不是越多越好。保留广告会降低有效内容密度，保留所有评论可能改变文章语义。决定是否保留评论，应来自目标语料的文体设计，并写进配置，而不是成为某个工具的隐含默认值。

## 四、规范化应该区分训练文本与匹配文本

“统一格式”听起来没有风险，实际每个操作都有信息代价。

Unicode NFC 与 NFKC 不等价。NFKC 会合并一些兼容字符，可能便利重复匹配，也可能改变有意义的字符形式；统一大小写方便检索，却可能损坏代码标识符；繁简转换会减少一些表面差异，也会改变地域用语和部分字形信息。使用这些操作之前，应明确它们用于哪一步。

一个稳妥的结构是保存三个层次：

1. `raw_text` 或可重新取得原文的位置，承担追溯职责。
2. `training_text`，只执行已经审查的内容变换。
3. `matching_text`，允许为了去重而进行额外规范化，但不能直接覆盖训练正文。

例如，正文中的 `API` 可以原样保留，而匹配副本按规则转成小写。最终指纹必须同时记录规范化版本，否则升级规则后，两次哈希的不同无法解释。

不可见控制字符、损坏编码和连续替换字符通常应被检测，但“发现异常”与“删除整篇”之间还有修复、隔离和人工抽查的空间。一个清洗流程最好能输出异常原因，避免所有失败都变成同一种空值。

## 五、语言识别是带误差的测量

语言识别模型输出的标签和分数，是模型对输入片段的判断。分数不能自动解释为经过校准的正确概率；不同语言、不同长度和不同领域的误差也未必相同。

对中文技术语料，仅使用汉字比例就存在明显边界。以下两类文本可能含有相近比例的汉字：一篇解释 CUDA、batch size 和 memory bandwidth 的正常教程，以及一张主要由产品型号、编号和零散汉字组成的目录。字符比例有用，但无法独立说明语义质量。

FineWeb2 对语言识别和阈值做了专门实验，并根据语言的分数分布调整处理。它还区分语言与文字系统，说明跨语言处理需要更细的配置。[FineWeb2 论文 §4.2](https://arxiv.org/html/2506.20920v1#S4.SS2)

中文流程可以保留文档级语言判断，同时对较长文本抽查多个段落。对于中英混排，先保留混排比例和段落标签，再决定是否分流到技术语料；不必把所有混排文本硬塞进“中文／非中文”的二元分类。

繁体文本也不应仅因字符集不同就被归为低质量。是否进行繁简转换，是模型覆盖范围和 tokenizer 设计的问题，需要独立决策。

## 六、把规则写成可解释的信号

规则过滤适合检测明显异常，例如正文过短、符号过密、重复行过多。重要的是定义分母、统计单位和作用范围。

重复行比例至少有两种算法。设非空行数为 $L$、不同非空行数为 $U$，可以定义：

$$
r_{\mathrm{line}}=\frac{L-U}{L}.
$$

也可以统计重复出现的行所占字符数：

$$
r_{\mathrm{char}}=
\frac{\text{首次出现之后的重复行字符数}}
{\text{全部非空行字符数}}.
$$

后一种定义需明确“首次之后”这一约定；有的实现会将重复组中所有行计入分子，两者不能混用。空文档应单独处理，不能通过给分母随意加一掩盖异常。

考虑一个教学算例：文档有十行，每行长度相同，其中五行是同一句话，另外五行各不相同。不同文本共六行，因此按“额外出现次数”统计，重复行比例为 $4/10=40\%$。如果重复的五行只是两个字的导航项，而其他五行各有一百字，字符占比会小得多。相同的阈值因此可能做出不同判断。

| 信号 | 可以发现什么 | 不能据此直接断言什么 |
| --- | --- | --- |
| 文本长度 | 空页、极短抓取、异常长拼接 | 短文没有知识价值 |
| 链接或模板占比 | 导航页、聚合页、模板残留 | 所有链接多的文档都无用 |
| 重复 n-gram | 循环文本、关键词堆叠 | 公式推导中的重复都是噪声 |
| 标点分布 | 部分列表垃圾或抽取失败 | 代码和诗歌必须像新闻一样断句 |
| 字符类别比例 | 乱码、编号堆积、目标语言不足 | 中英混排就是低质量 |

英文规则中的词长、停用词密度和句末标点，依赖英文的分词与书写习惯。中文不能直接用 `split()` 得到有相同含义的词数。最基本的做法是明确每个信号使用字符、分词结果还是模型 token，并分别观察中文与英文分布。

## 七、保留率需要按阶段和分组解释

假设一份自拟语料有一百万条记录：抽取后保留八十万条，语言过滤后保留六十万条，规则过滤后保留四十八万条。最后一步的阶段保留率是 $48/60=80\%$，相对原始输入的累计保留率是 $48/100=48\%$。两种数字都成立，回答的问题不同。

文档保留率还不能代替 token 保留率。大量短页面被删除时，文档数降幅可能很大，而训练 token 降幅较小。完整报告应同时列出文档、字节和 token 的变化，并按语言、领域、来源及长度分桶。

过滤顺序也需要说明。若广告页同时触发短文本和重复规则，先执行哪条，就会改变“首个拒绝原因”的统计。可以同时保存所有触发标签与最终决策，再用一个明确的优先级确定主原因。不要把按顺序统计的删除数当成每条规则独立贡献的效果。

清洗操作通常不能任意交换：先删行会改变文档长度，先规范化会改变重复匹配，先去重会改变后续评分的工作量和样本分布。第六篇会把这些依赖组织成可重建的处理图。

## 八、隐私处理与内容质量分别评估

个人信息检测可以采用模式、实体识别和上下文规则。模式适合发现部分邮箱或 IP，不能覆盖姓名、地址、账户信息和上下文关联；反过来，数字也不一定是个人信息。日期、版本号、数学常数和产品编号不能只因为形似某种模式就一律删除。

可以根据数据用途选择片段替换、整篇隔离或来源级排除，并记录决策。保存多个原始副本也会增加管理成本，所以追溯所需的原文应有受控存储与保留范围，不必公开到博客或数据样例中。

关键词内容过滤同样需要审查上下文。描述某个社会问题的正常文章可能含有被屏蔽的词；只有关键词列表，无法区分讨论、引用与鼓励。对 C4 的研究发现其过滤过程对不同群体相关文本有不同影响，这说明过滤规则会改变语料代表性。[Dodge 等，EMNLP 2021](https://aclanthology.org/2021.emnlp-main.98/)

对于这类信号，适合分别记录内容类型、检测置信度和处理结果，而不把所有维度合并成一个叫“quality”的分数。

## 九、怎样判断清洗改动值得保留

审计需要看四类样本：稳定保留、稳定拒绝、阈值附近、旧版与新版决策发生变化的样本。最后一类尤其有用，它直接揭示改动影响了什么。

人工抽查最好隐藏规则名称和新旧版本标签，减少“新算法应该更好”的预期影响。审查者可以分别标注正文完整性、可读性、领域价值、模板残留，而不是只给一个总分。若按分桶定额抽样，汇总总体指标时要还原各桶权重。

数据层审计通过之后，训练层还需要受控比较：固定模型、tokenizer、实际训练 token、优化设置与评测。训练效果较好，才说明该清洗改动在这些条件下有效；删除率高或人工觉得文本更整齐，都不是充分证据。

如果当前预算只够数据审计，依然能形成有价值的结论，例如“新抽取器减少了导航残留，但更容易漏掉代码块”。这类结论是可观察、可修正的工程事实，不需要包装成模型能力提升。

## 十、从工具到自己的处理配置

[DataTrove](https://github.com/huggingface/datatrove)提供可组合的读取、过滤、去重与写出组件；它的[FineWeb 示例](https://github.com/huggingface/datatrove/blob/main/examples/fineweb.py)适合对照论文观察一个流程如何拆成任务。学习时重点看输入输出、拒绝记录、阶段依赖和配置，不要只复制阈值。

对个人项目，先实现清楚的阶段接口，再考虑大规模执行。每个阶段至少输出保留记录、拒绝原因、处理计数与配置版本。将异常与正常拒绝分开，避免网络读取失败被误当成“质量不合格”。

| 关键判断 | 依据 | 边界 |
| --- | --- | --- |
| 抽取方式会影响后续训练结果 | FineWeb 的受控实验 | 结论受其模型、数据和评测限制 |
| 统一阈值不一定适用于多种语言 | FineWeb2 的语言适配研究 | 本地阈值仍需审计 |
| 过滤改变的不只是噪声量 | C4 分析与本文样例推演 | 各来源影响程度不同 |
| 保留正文、匹配副本和处理版本有助于追溯 | 本文工程设计 | 增加存储与维护成本 |

可以用两个问题检查理解：为什么规范化后得到的去重文本不一定适合直接训练？如果新规则让中文技术文章的保留率明显下降，你会先检查哪些信号，再决定是否放宽阈值？
