训练到一半，程序退出了。如果已经保存了模型权重，重新加载后继续训练，是否就等于从来没有中断过？

不一定。权重只描述当前模型的参数；训练过程还有优化器、学习率、随机数和数据顺序。少保存一项，恢复后可能仍然能运行，但接下来的更新已经走上另一条轨迹。

## 模型以外，还有哪些状态

假设模型刚做完第 80 次更新。要继续第 81 次，至少要回答：

| 状态 | 为什么需要 |
| --- | --- |
| 模型参数 | 保留当前已经学到的权重。 |
| 优化器状态 | Adam 等优化器保留梯度统计；清空它们会改变后续更新。 |
| 学习率调度状态 | 避免从计划的开头重新升温或衰减。 |
| 随机数状态 | 影响数据打乱、dropout 等随机行为。 |
| 数据排列与当前位置 | 避免漏掉或重复读取训练样本。 |
| 配置及数据、分词器指纹 | 检查恢复时是否使用了相同输入和训练条件。 |

如果梯度累积跨越保存时刻，还要额外考虑未完成更新的梯度和累积进度。本项目的恢复检查以已有实现和检查点边界为准，不能自动推及任意保存时刻。

## 如何检查“继续”

我对同一个小文本实验做了两条路径：一条不中断地训练到第 160 步；另一条在第 80 步保存，在新进程加载后继续到第 160 步。比较数据顺序、优化器步数、学习率进度、有效 token、最终权重、验证损失和固定提示生成。

新进程很重要。只在原进程里重新读取文件，可能依赖了没有写入检查点的内存对象，掩盖真正的问题。

## CPU 与 MPS 的观察

项目的 CPU 自动测试覆盖了连续训练与中断恢复的逐项权重一致性。在这项检查中，恢复结果满足测试条件。

MPS 上的同一小文本实验则没有通过 `1e-6` 的严格权重比较：连续与恢复的最大权重绝对差约为 `6.36e-5`；两次都不中断的训练之间也观察到约 `6.82e-5` 的最大差异。这个对照说明数值差异不只出现在恢复路径，但单凭这一次观察，不能给所有 MPS 训练指定误差范围或解释全部来源。

在本次实验中，两条路径的最终验证 NLL 相差约 `2.19e-8`，固定贪心生成的 token 序列相同。这是当前条件下的行为证据，而不是跨设备逐位一致的保证。

## 恢复成功不只有一个标准

如果研究需要严格重现每个参数，比较权重和随机状态很重要；如果关注的是一次长训练能否可靠续跑，还需要看训练计划、样本顺序、验证表现和生成行为。判断标准应在实验前写清楚。

我的做法是把检查点当作训练状态的一部分，而不是只当作模型文件：保存完整状态，在新进程恢复，验证数据和代码身份，并报告实际观察到的数值差异。这样即使结果不完全一致，也能更清楚地定位问题。
